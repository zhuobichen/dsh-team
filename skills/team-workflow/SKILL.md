# 多 Agent 团队接力工作流

当任务**足够复杂**（多模块、多步骤、需要多种能力协作）时，不要试图一个人完成。把任务交给一个「角色化团队」，按下面的接力顺序完成。

## 团队角色与接力顺序

```
team-lead ──► analyst ──► coder ──► reviewer ──► tester ──► team-lead（汇总）
```

| 角色 | 职责 | 输入 | 输出 |
|------|------|------|------|
| `team-lead` | 分解任务、分配、汇总交付 | 用户需求 | 任务分解 + 最终交付 |
| `analyst` | 需求分析、方案设计 | 子任务 | 实现方案/设计 |
| `coder` | 写代码实现 | 方案 | 代码 |
| `reviewer` | 质量把关、代码评审 | 代码 | 评审意见 |
| `tester` | 验证测试 | 代码+意见 | 测试结果 |

## 执行规范

1. **分解**：team-lead 先把复杂任务拆成 2-5 个可独立完成的子任务。
2. **委派**：每个子任务用 `subagent` 委派给对应角色（`analyst`/`coder`/`reviewer`/`tester`），角色通过各自 SKILL.md 的 persona 与职责约束。
3. **接力**：上一个角色的**输出**是下一个角色的**输入**，不跳跃、不遗漏。
4. **评审闭环**：reviewer 发现问题 → 回给 coder 修改 → 再评审，直到通过。
5. **测试闭环**：tester 验证不通过 → 回给 coder 修复 → 再测试。
6. **汇总**：team-lead 收集所有角色的产出，整合成最终交付，附上各环节的结论。

## 关键原则

- **能委派就委派**：每个子任务交给专门的 subagent，不要自己硬编码。
- **输出可交接**：每个角色的产出要结构化、可被下一角色直接使用。
- **问题不积压**：评审/测试发现的问题立即回传，不拖到最后。
- **小任务不套团队**：简单任务（改一行、查个值）直接自己做，不要过度编排。
